Prevent half a transfer from reaching the ledger

Commit or roll back a balanced two-account movement as one operation.

Theory and terminology

Transaction atomicity and idempotency

database transactions · rollback · retries · ledger

What you should be able to explain

  • Commit or roll back a balanced two-account movement as one operation.
  • Handle duplicate requests safely and detect a reused ID that describes a different transfer.

Treat the economic event as one write boundary

A €125 internal transfer is one instruction with two cash legs, a reduction in one account and an increase in another. Storing a negative amount, committing it, and then separately crediting the destination leaves a moment when the recorded total is wrong. An after-the-fact report can detect it, but detection cannot make an inconsistent statement issued in between correct.

Atomicity means all writes in the transaction take effect together or none do. Isolation controls what competing operations can see or do while it runs. Durability concerns retention after a successful commit. A balanced transfer rule is an application invariant: its signed legs must sum to zero for the same event and currency.

Make retries have one financial effect

A timeout after the database commits can leave the caller unsure of the outcome. Give the economic event a stable key before the first attempt and reuse it after a timeout. If that key already exists with the same payer, recipient and cents, return the earlier result. If the payload differs, preserve the existing posting and raise a conflict.

A prior lookup on its own can race with another writer. A uniqueness constraint and the transaction's concurrency behavior close that gap. In the SQLite demonstration BEGIN IMMEDIATE reserves the writer role before reading the key. A second writer may wait or receive a busy error. On a recoverable busy result, retry the whole operation with its original key.

Reconcile by event as well as in total

An event header, two distinct accounts and equal opposite integer amounts make the proof simple. Reconciliation must count events, validate both legs and verify that each pair sums to zero. An organization-wide net sum can conceal one transfer missing its debit and another missing its credit by the same amount.

The example treats the accounts as a common pool of cash in one currency and permits negative balances. A system prohibiting overdrafts would need to verify available funds within the same transaction. A cross-currency movement requires separate currency balances, exchange rates and balancing accounts. The two equal opposite cent amounts would no longer describe the whole event.

Method

Build the result

For each new id, commit header plus (source, −c) plus (destination, +c). Existing id + identical payload → replay; existing id + different payload → conflict.

id is a stable transfer identifier. c is a positive integer in cents of one currency. A leg is one signed account movement. A replay acknowledges a previously completed request.

  1. Validate distinct accounts, positive integer units and the intended currency before writing.
  2. Open a transaction, check the key under the database's write protection, then insert the header and both legs for a new event.
  3. Commit once. On an intervening error roll back, and reconcile each posted event's paired entries before producing balances.
Worked case

A retry-safe transfer in Python and SQLite

Start with an empty in-memory single-currency ledger. Transfer 12,500 cents from cash to reserve with ID T7. The standard-library code below can also simulate termination of the unit of work by raising an exception after the first leg.

Working

  1. import sqlite3
db = sqlite3.connect(':memory:', isolation_level=None)
db.execute('PRAGMA foreign_keys = ON')
db.execute('CREATE TABLE event (id TEXT PRIMARY KEY NOT NULL, src TEXT NOT NULL, dst TEXT NOT NULL, cents INTEGER NOT NULL)')
db.execute('CREATE TABLE leg (id TEXT NOT NULL REFERENCES event(id), account TEXT NOT NULL, cents INTEGER NOT NULL, PRIMARY KEY(id,account))')
def post(key, src, dst, cents, stop=False):
    if not key or not src or not dst or src == dst or type(cents) is not int or cents <= 0:
        raise ValueError('invalid transfer')
    db.execute('BEGIN IMMEDIATE')
    try:
        old = db.execute('SELECT src,dst,cents FROM event WHERE id=?',(key,)).fetchone()
        if old is not None:
            if old != (src,dst,cents):
                raise ValueError('conflicting transfer ID')
            db.execute('COMMIT')
            return 'already posted'
        db.execute('INSERT INTO event VALUES (?,?,?,?)',(key,src,dst,cents))
        db.execute('INSERT INTO leg VALUES (?,?,?)',(key,src,-cents))
        if stop:
            raise RuntimeError('simulated interruption')
        db.execute('INSERT INTO leg VALUES (?,?,?)',(key,dst,cents))
        db.execute('COMMIT')
        return 'posted'
    except Exception:
        if db.in_transaction:
            db.execute('ROLLBACK')
        raise
  2. Calling post('T7','cash','reserve',12500,stop=True) raises the simulated error. Catch it in a driver if making further calls. The rollback leaves zero event rows and zero legs.
  3. Calling post('T7','cash','reserve',12500) now succeeds and leaves one header and signed legs of −12,500 and +12,500 cents. The event sum is zero.
  4. The same successful call a second time returns 'already posted' and preserves two legs. Requesting 13,000 cents with ID T7 instead raises a conflict without modifying the original 12,500-cent posting.

Decision and interpretation

Each completed transfer changes the two account balances once. This transaction covers this database only. An external bank message requires a separate delivery and reconciliation design.

Quick check
Which evidence is sufficient to acknowledge a retry as the same transfer in this example?

A stable ID has meaning only with the same payload. Total balance and amount alone do not establish identity.

Written practice

Independent exam problem

A queue delivers X9, a £75 transfer from A to B. The database commits both legs but the worker loses the network acknowledgment. On reconnect it receives the same X9 and then an X9 asking to send £80 instead. Give ledger balances and responses relative to opening balances.

Reveal the worked solution
  1. The original commit means A has −7,500 pence and B +7,500 pence relative to opening. The header records A, B and 7,500.
  2. On the identical retry compare the existing payload and acknowledge the prior posting. There are still two legs for X9.
  3. Reject and record the changed £80 payload for investigation. The original legs remain unchanged. Any authorized correction needs its own researchable reversal or adjustment event.

Interview practice

Explain it aloud

A worker stops after writing the first side of a transfer. Can a later report see money vanish?

Saved on this device as you type.
Compare with a spoken answer

Put the event and both legs in one database transaction. A rollback removes the first write, and a commit publishes all three together. Keep a unique request ID and its payload so a retry cannot move the money twice.

Interviewer’s follow-up

Could recording both legs in one transaction prevent a client from intentionally or accidentally sending a second transfer with a new valid ID?

Compare with the follow-up answer

No. Atomicity applies within each event and this idempotency check recognizes reused IDs. A second business instruction needs stronger upstream identity or an explicit duplicate-review rule.
