Tests and reconciliation

Test positive and negative cases, check balances and compare a sample calculation with a second method before trusting a long pipeline.

The starting point

A financial report that adds up can still contain the wrong trades. Tests give a model small known cases with expected results. Reconciliation compares its totals with an independent record or with a separately derived identity.

Combine checks that catch different mistakes. For a cash ledger, test that debits and credits have the intended sign, duplicate identifiers are handled, and an empty list produces the opening balance. Checking the same formula twice can simply repeat the same error.

Theory and method

Double-entry reconciliation and netting controls

Control total · Gross debit and gross credit

An imported bank file matches the expected closing cash. How could it still contain two material transaction errors?

A cash movement report can get its signed total right while omitting a receipt and accidentally including a payment of the wrong amount or direction. Two opposite mistakes can cancel. Reconcile the identity for ending cash, but also check gross receipts, gross payments, count and stable transaction IDs against the independent bank record. Each control examines a different property, so the combination can isolate errors hidden by the closing balance alone.

How the result is built

Closing cash = opening cash + Σ receipts − Σ payments. Reconcile gross receipts, gross payments and ID sets independently.

Cash, receipts and payments use the same currency and cutoff. A stable ID distinguishes an economic event from an identical-looking euro amount. Σ adds amounts in the named set.

  1. The bank shows opening €100, a €50 receipt and a €20 payment. Closing cash is €130. The import shows a €70 receipt and a €40 payment and also closes at €130.
  2. Gross receipts are overstated by €20 and gross payments by €20, offsetting in the net. Comparing both gross control totals exposes the error immediately.
  3. Match IDs and source records to find whether the two rows were misread, duplicated or belonged to another account. Correct records using the approved process and rerun all controls.

When the reasoning holds

  • The control record must be sufficiently independent and use the same account, currency and period. Comparing two extracts from the same broken transformation can reproduce the same error.
  • Know whether balances and checks use settlement or trade dates. Legitimate timing differences require a documented bridge before treating them as discrepancies.
First example

Start with €100, add a €30 receipt and subtract a €12 payment. Expected closing cash is €118. A duplicated receipt produces €148. Compare against the bank statement and check unique transaction identifiers to locate the discrepancy instead of forcing the total to match.

Tests answer different questions

A function-level test gives a small component known inputs and checks expected outputs, such as a return of zero for unchanged known prices. An integration test checks several components together, for example loading raw transfers, attaching currency conversions and grouping by account. Either type can pass while the other fails.

Reconciliation compares an output with an independent record or accounting identity. A second formula copied from the same erroneous cell offers limited independent evidence. Use a bank statement, a separate calculation from raw inputs, or balances recorded by a different process. If two systems share the same erroneous source, note the remaining common risk.

Invariants and negative cases

An invariant is a condition that must hold for all permitted inputs, such as closing cash equalling opening cash plus net posted movements. Other useful checks are unique transaction IDs where required, probabilities summing to one, weights matching net invested capital, or counterpart entries summing to zero for an internal transfer.

A negative test deliberately supplies invalid input such as a missing currency, duplicated ID, zero starting price or date outside the reporting period. Choose whether the process should raise a clear error, quarantine the input, or use a documented missing result. A test that merely confirms the job did not crash leaves the most important outcome unchecked.

Safe retries and tolerances

A payment feed can send yesterday’s transactions again after a timeout. If reprocessing adds every record again, balances change even though the economic events are identical. An idempotent process produces the same final state when the same input is applied again. Stable transaction IDs and an explicit correction policy make this behaviour testable.

When reconciling values, distinguish a permitted rounding tolerance from an unexplained economic difference. Currency rounded to cents per transaction can differ from rounding a net aggregate. State which the contract or statement uses. Maintain an exception list with IDs and amounts so allowed tolerances do not conceal repeated systematic differences.

Method

Design a small but sharp test set

  1. Build a known fixture

    Use a tiny ledger where opening balance, transaction signs, currency and expected close can be independently recomputed.

  2. Introduce adversarial data

    Replay an ID, omit a required field, reverse a sign or supply a correction. Specify exactly which records should be accepted and why.

  3. Cross-check and explain

    Compare the fixture total with an independent record, report individual exceptions, and ensure a retry leaves verified balances unchanged.

Worked case

A ledger replay after a timeout

An account starts at €500. The file contains T1 +€70, T2 −€25 and T3 +€15. A retry delivers T2 again with precisely the same stable ID and content. The bank statement closes at €560.

Working

  1. Unique legitimate transfers net €70 − €25 + €15 = €60. Expected close is €560.
  2. Blindly appending the retried T2 produces €535, a €25 shortfall. Matching its ID and content to an already posted event leaves the verified close unchanged.
  3. If a later record has ID T2 but amount −€35, it is a conflicting version rather than an identical replay. Route it through the explicit correction process before deciding the new balance.

Interpretation

A statement-level difference identifies the amount, while the source ID isolates the cause. A system that silently deduplicates every same-amount transfer could drop real transactions with different IDs.

Trace a forecast and test a boundary case

def lowest_cash(opening, flows):
    cash = lowest = opening
    for flow in flows:
        cash += flow
        lowest = min(lowest, cash)
    return lowest

assert lowest_cash(20, [-12, -15, 20]) == -7
assert lowest_cash(20, []) == 20

The lowest position is −7 on day 2, even though closing cash is 13. The second test defines the empty-input behavior. Initializing the minimum to zero would also return zero for an all-positive path and misstate its cushion.

A common mistake

Two different customer payments of the same amount are removed because their euro figures match.

How to correct it

Deduplicate using stable event identity and required attributes, not amount alone. Legitimate transfers can share dates and values while belonging to different customers.

Quick check
Swapping all receipts and payments happens to yield the right total in one balanced month. Which test best exposes the sign error?

With an opening €100 and a lone €30 receipt, the known outcome is €130. A reversed sign yields €70, allowing the test to isolate the mistake.

Written practice · 8 marks

Independent exam problem

A cash ledger opens at €220 and contains K1 −€40, K2 +€100, K3 −€20, then a repeated identical K2. Two separately identified €20 payments are also possible in other files.

  1. Part A · 5 marks

    Find the correct and naive closing balances and specify two tests for replay behaviour.

  2. Part B · 3 marks

    How should testing distinguish a duplicate replay from two legitimate equal-amount transfers?

Reveal the worked marking guide

Part A 5 marks

Unique records net −€40 + €100 − €20 = €40, so correct close is €260. Naive append gives €360. Assert the first run closes at €260 and that running the identical file again leaves counts and balances unchanged.

Part B 3 marks

Use distinct stable IDs and supply both examples in a fixture. Same ID and same content should post once, while different IDs with identical amounts should both post if valid. Conflicting content on the same ID should trigger the defined correction policy.

Interview practice

Explain it aloud

An imported bank file matches the expected closing cash. How could it still contain two material transaction errors?

Saved on this device as you type.
Compare with a spoken answer

I would withhold sign-off until the gross cash and ID controls also agree. Starting from €100, both files close at €130, but our import exaggerates both receipts and payments by €20. That can corrupt customer balances, classifications and management reporting even with a correct net cash figure. I would match the underlying IDs and independently confirm the bank entries before posting corrections.

Interviewer’s follow-up

If both gross totals and the row count now also match, is the control complete?

Compare with the follow-up answer

Equal gross totals and counts still allow a missing payment to be replaced by a different equal-value payment. I would compare the stable ID sets, signed amount and account on each matched ID and investigate exceptions. Where fraud or authorization matters, underlying approval evidence provides an additional independent control.
