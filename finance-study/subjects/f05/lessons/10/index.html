Reproducible research

Preserve original data, code versions and transformations. A fresh run should reproduce both the numbers and the figures cited in the analysis.

The starting point

A colleague wants to repeat a chart six months after you publish it. The data supplier may have corrected old observations, your software may have changed, and the manual filters you used may be difficult to remember. A chart alone cannot show which choices produced it.

Keep the original input version, the transformation code, the package versions and a record of parameters and dates. Fix a random seed for simulations when appropriate. Regenerate the chart and its cited number in one workflow so changes in data propagate to both.

Theory and method

Content-addressed data provenance

Checksum · Reproducible build

A colleague reruns your notebook and gets the published chart. What additional evidence would show they used the same input data?

A chart can look identical even when some underlying rows changed or the rounding concealed a small revision. Record a digest of the exact input bytes before transforming them. A cryptographic hash produces a compact fingerprint that is extremely sensitive to byte changes. Combine it with code version, environment and parameter information so a later analyst can distinguish a changed input from a changed calculation. A verified fingerprint alone says nothing about the truth of the original figures.

How the result is built

import hashlib
raw = b"id,value\nA,4\nB,6\n"
digest = hashlib.sha256(raw).hexdigest()
assert digest == hashlib.sha256(raw).hexdigest()

raw is the exact input byte sequence; b denotes Python bytes, \n encodes line breaks, hashlib.sha256 computes the SHA-256 digest and hexdigest renders it as hexadecimal text. The assertion checks deterministic equality on identical bytes.

  1. Hash original raw bytes before parsing. Reordering rows, changing line endings or altering an amount changes the byte sequence and normally produces a different digest.
  2. Store the hash with the input version, acquisition time, schema, code revision, dependency versions and analysis parameters in a run manifest.
  3. For a semantic comparison, also build an explicitly normalized table and hash its canonical bytes separately. Preserve both digests so input-byte changes and economically equivalent formatting changes remain distinguishable.

When the reasoning holds

  • Hashes are computed on exactly specified bytes using the same algorithm. A spreadsheet re-saved by another application can change raw-file bytes even when cell values agree.
  • A trustworthy reference digest and authorized access to the input version are required. Comparing a file against a hash generated from that very file during the same unaudited rerun proves little about provenance.
Terms in this lesson
Percentage point
The difference between two percentages. A rate rising from 4% to 5% rises one percentage point.
First example

A report’s figure shows 4.2% average growth for 92 firms. A fresh run gives 4.5% for 95. Compare the saved list of firm identifiers and source version first. Three newly eligible firms can change the estimate even if the chart formatting and calculation code match.

Reconstruct the number, then the claim

A chart in an investment report depends on choices about the universe, the time window, the data vintage, the handling of corporate actions, the calculation, and the plotting specification. Reproducibility means someone with appropriate access can run the recorded procedure on the same inputs and recover the same results within a stated tolerance.

Replication using a genuinely new sample or a different source asks a further question about robustness. An exact reproduction can succeed even when the original model has a conceptual error. Reproduction establishes traceability. Independent checks on theory, source quality and generalization remain necessary.

Capture a point-in-time recipe

Retain a read-only original extract or an exact versioned source reference, a checksum for identifying the bytes, acquisition date, schema and units, code revision and the parameters used. A checksum shows whether two inputs are identical at the byte level. It does not prove a series is correct or legitimately obtained.

Record software and package versions and any relevant time-zone or calendar configuration. For stochastic simulations record generator type, seed and how observations were ordered before drawing. A fixed seed controls pseudorandom variation under the same algorithm, but it does not freeze a vendor feed, library changes, concurrency effects or financial assumptions.

Separate revisions from reproduction failures

A supplier may revise economic history after new filings arrive. Keep the archived run and treat the refreshed data as a new vintage. Comparing results side by side can reveal the effect of revisions. Replacing old inputs without a record makes it impossible to distinguish a deliberate update from a hidden change in methodology.

Define the verification target before running. Check the selected IDs and row count, set a tolerance for numerical results, and verify that each chart agrees with the table built from the same totals. Rebuilding visual output from the same numeric table avoids hand-keyed labels drifting away from the source result.

Method

Build a reproducible report

  1. Pin the inputs

    Record the input snapshot, stable identifiers, calendar, version, data dictionary and eligibility rules before transforming records.

  2. Run a single procedure

    Apply clean transformations in recorded order under named code and environment versions. Generate tables, summary and chart using the same derived data.

  3. Preserve evidence

    Save row counts, checksums, key aggregates and exception IDs for comparison. Label later vendor corrections as new analysis vintages.

Worked case

An index that gained two companies

An archived analysis included three firms with returns 2%, 4% and 6%. A later download for the same dates adds two firms at −5% and +3%. Code and equal-weighting rules are unchanged.

Working

  1. Original mean was (2 + 4 + 6)/3 = 4%. The new input gives (2 + 4 + 6 − 5 + 3)/5 = 2%.
  2. Compare lists of firm identifiers. The original three results did not change. The new firms contributed −2 percentage points to the numerator while increasing the denominator to five.
  3. Running the old snapshot with the old code should regenerate 4%. Running the revised snapshot legitimately yields 2%. A transparent report labels which question uses the original universe and which uses the revised history.

Interpretation

A fixed plotting style or random seed would not explain this difference. The source membership changed, so input identity and inclusion records are decisive.

At the board

Draw the label horizon before splitting the data

A signal at the end of trading day t uses information already released by that close. Its target is the return from close t to close t+3. The first validation prediction is formed at the close of day 10. Freeze all training inputs and labels at the close of day 9.

If all features through day 9 are assigned to training, three labels bring later prices back across the boundary. Purge those rows or move the training cutoff. Fit transformations such as scaling and feature selection only on eligible training rows, freeze the procedure, and score the later block. Validation targets may overlap one another too, which changes performance uncertainty.

A common mistake

A report states that it can be reproduced because it includes a live link and a chart screenshot.

How to correct it

A live source can change and a chart omits calculation choices. Preserve an exact input version and a runnable transformation that produces the displayed statistic.

Quick check
What would most directly support reproducing the original 4.2% figure?

Those items let another analyst reconstruct both the chosen firms and the calculation. They can then compare any later update with the original on a like-for-like basis.

Written practice · 8 marks

Independent exam problem

An old report shows four equal-weight returns of 1%, 3%, 5% and 7%. The current source revises 7% to 5% and adds a fifth firm returning −4%. The rerun uses identical code.

  1. Part A · 5 marks

    Decompose the new result into the change from revising the original four and the subsequent universe change.

  2. Part B · 3 marks

    Name the minimum evidence needed to attribute these changes to inputs, and one reason this still would not validate the investment claim.

Reveal the worked marking guide

Part A 5 marks

Original mean is 16/4 = 4%. Revised original four average (1 + 3 + 5 + 5)/4 = 3.5%, a −0.5-point revision. Adding −4% gives 10/5 = 2%, another −1.5 points. Total change is −2 points.

Part B 3 marks

Match input versions, stable IDs, per-firm values, code revision, weighting rules and comparable dates. Even exact reproduction may inherit selection bias, a weak economic hypothesis or costs omitted from the calculation.

Interview practice

Explain it aloud

A colleague reruns your notebook and gets the published chart. What additional evidence would show they used the same input data?

Saved on this device as you type.
Compare with a spoken answer

I would ask for the archived raw-input digest and independently rehash the input they used. I would then compare code revision, packages, eligibility rules and key numerical outputs. If only a new export’s formatting differs, a separately defined canonical-table fingerprint can help show the economic data agree. None of these checks alone establishes that the original model was economically valid.

Interviewer’s follow-up

If the team sorts rows before hashing, could the technique hide a meaningful change?

Compare with the follow-up answer

Yes if row order itself carries information, such as event order for trades sharing a timestamp. I would include a stable sequence field in canonicalization when ordering matters and retain the original raw hash in every case. A changed raw hash and unchanged normalized hash then have a clear interpretation.
